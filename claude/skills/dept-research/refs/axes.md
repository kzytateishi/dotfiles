# 判断軸のライブラリ

調査の質は、**着手前に判断軸を決められるか**でほぼ決まる。軸が無い調査は「調べたこと全部」を並べた報告になり、読み手が自分で判断し直す羽目になる。

このファイルは軸の**引き出し**。全部使うためのものではない。調査類型ごとに眺めて、今回効く軸を選ぶ。

## 軸の選び方(全類型共通)

- **3〜6 本に絞る。** 10 軸の比較表は読めない。落とした軸は「今回は見ない」と報告に書く
- **差がつかない軸は落とす。** 全選択肢が同じ評価になる軸は判断に寄与しない。表の飾りにしかならない
- **重みを付ける。** 全軸が同じ重みの表からは結論が出ない。「最優先はこれ、次点はこれ」を先に決める
- **可逆性の軸を必ず 1 本入れる。** 出口・撤退・移行のコスト。入る判断だけして出る判断ができない調査が一番多い
- **今日のコストでなく 2 年後のコストで測る。** 導入コストは 1 回、運用コストは毎月

> 軸をユーザーに聞くときは「何を重視しますか」と抽象的に聞かない。**「この 3 つならどれを優先しますか」と候補を出して選ばせる。** 選択肢のない質問は答えが返ってこない。

## 最後に必ず当てる 3 つ(類型を問わず)

| 問い | 見落とすと起きること |
|---|---|
| **「やらない / 現状維持」を選択肢に入れたか** | 導入前提で比較し、一番安い選択肢(何もしない)が表に載らない |
| **「今決めない」コストを見積もったか** | 情報が出揃う 3 ヶ月後に決めれば済む話を、今の不完全な情報で不可逆に決める |
| **決定を覆すコストは可逆か不可逆か** | 可逆な決定に 3 日かけ、不可逆な決定を 10 分で下す。時間の配分が逆になる |

## 1. 技術・ライブラリ選定

| 軸 | 具体的に何を見るか | この軸を見落とすと起きること |
|---|---|---|
| **学習コスト** | チームの既知概念からの距離。ドキュメントの厚さ。エラーメッセージが原因を指すか | 導入は 1 日で終わるが習熟に 3 ヶ月かかり、その間の PR が誰にもレビューできなくなる |
| **保守体制とバス係数** | 直近 12 ヶ月のコミット頻度・コミッタ人数・issue の放置期間・企業バックの有無 | メンテナ 1 人が離れた翌月に脆弱性修正が止まり、自前 fork を保守する側に回る |
| **ロックインの深さ** | そのライブラリの API が自分のコードのどこまで染み出すか(型・ディレクトリ構成・ビルド・デプロイまで侵食するか) | 乗り換えの見積もりが「1 画面」ではなく「全画面」だったと移行当日に知る |
| **出口(移行コスト)** | 抜けるときにデータとコードをどう持ち出すか。標準形式へのエクスポート。互換レイヤの有無 | 不満を抱えたまま 3 年使い続ける。出る判断ができないので入る判断も雑になる |
| **実績** | GitHub star ではなく**自分と同規模・同ドメインの本番運用事例**。壊れたときに検索して情報が出るか | star 3 万だが自分の構成(SSR / モノレポ / その DB)の事例はゼロで、踏むバグが全部世界初になる |
| **型・テストのしやすさ** | 型定義が本体同梱か第三者提供か。`any` の量。モックできるか。公式のテストユーティリティがあるか | テストを書くために本番コードを歪める。あるいはその層のテストを諦める |
| **バージョン方針と EOL** | semver を守っているか。メジャーの頻度と移行ガイドの質。LTS の有無とサポート期限 | メジャー更新のたびに他の作業が止まる。あるいは更新を諦めて脆弱性を抱えたまま塩漬けにする |
| **依存の重さ** | 推移的依存の数、バンドルサイズ、ネイティブ拡張の有無 | CI が遅くなる。攻撃面が増える。特定の CPU / OS イメージでビルドできず本番だけ落ちる |
| **ライセンス** | ライセンス種別と**その変更履歴**(近年 BSL / SSPL 等へ変更した前例がないか) | 次のメジャーでライセンスが変わり、自社の提供形態では使えなくなる |
| **既存構成との相性** | 現行のランタイム・ビルドツール・型システム・デプロイ先で動くか | ローカルでは動いたが本番のランタイムで動かない |
| **段階導入できるか** | 一部機能だけで試せるか、all-or-nothing か | 試すために全面書き換えが要るので、**試さずに決める**ことになる |

> ライブラリ比較で最も多い事故は「機能表で勝った方を選び、保守体制と出口を見なかった」。機能は追いつく。保守体制は追いつかない。

## 2. SaaS・ツール導入

| 軸 | 具体的に何を見るか | この軸を見落とすと起きること |
|---|---|---|
| **料金体系の伸び方** | 課金単位(シート / 実行数 / データ量 / API コール)が、自分の事業で**一番伸びる変数**と一致していないか。無料枠の崖の位置 | 導入時は月 5 千円。人が 3 人増えた月に 8 万円になり、乗り換えるには既に依存が深い |
| **最低契約単位・支払い条件** | 最低シート数、年契約縛り、途中解約時の返金可否、値上げ時の告知条件 | 合わないと 1 ヶ月で分かるのに、残り 11 ヶ月払い続ける |
| **出口(データの持ち出し)** | エクスポート形式(構造化データか PDF か)。API で全件取得できるか。解約後の保持期間 | 解約した瞬間に 3 年分の履歴が読めなくなる。移行しようにも PDF しか出せない |
| **権限管理の粒度** | ロールの種類、外部ユーザー / ゲストの制御、SSO・SCIM が上位プラン限定か | 業務委託に見せられない情報が同じ空間にあり、面倒になって結局全員を管理者にする |
| **監査ログ** | 誰が何を見た / 変えた / 消したが残るか。保持期間。エクスポートできるか | 事故が起きてから「誰が消したか分からない」と気づく |
| **SLA と実績** | SLA の数値だけでなく**補償の中身**(返金クレジットのみか)と、ステータスページの過去履歴 | 99.9% を根拠に業務を乗せたが、止まった日の損失は自分持ちで、補償は月額の数 % のクレジットだけ |
| **サポートの言語と時間帯** | 日本語対応の有無、初回応答時間の保証、それが上位プラン限定か | 障害が自分の営業時間に起き、返信は翌々日の英語メールで来る |
| **データの所在とコンプライアンス** | リージョン選択の可否、サブプロセッサ一覧、第三者認証の有無 | 顧客のセキュリティ監査で使用ツールのデータ所在を答えられず、案件が止まる |
| **既存ツールとの重複** | 既に契約しているもので 8 割足りないか | 機能が大きく重なるツールを 2 つ払い続け、どちらも中途半端に使う |
| **管理コスト** | アカウント棚卸し、退職 / 契約終了時の削除、請求書処理の手間 | ツール 1 個あたり月 30 分の管理が、20 個で丸 1 日になる |
| **連携の実在** | ドキュメントの「連携対応」が、**欲しいイベント・欲しい粒度**で本当に使えるか。レート制限 | 「連携あり」と書いてあったが、必要な webhook だけ無く、ポーリングを自作する |

> 料金は必ず**自分の 1 年後の数値を入れて再計算する**。公式の料金表を転記しただけの比較は、一番効く軸を評価していない。

## 3. 制度・法令の調査

他の類型と違い、これは「選択肢の比較」ではなく「読み違えていないか」の調査。軸は**読み違えの型**に対応する。

| 軸 | 具体的に何を見るか | この軸を見落とすと起きること |
|---|---|---|
| **適用対象** | 誰に / 何に適用されるか。事業規模・業種・取引形態の閾値と、その**数え方** | 適用外だと思っていたが、従業員数の数え方に業務委託や短時間勤務が含まれていた |
| **施行日と経過措置** | 公布日 / 施行日 / 適用開始日は別物。既存契約に遡及するか。猶予期間の終期 | 対応済みのつもりが施行は来年だった。あるいは逆に猶予期間が既に終わっていた |
| **参照した条文が現行版か** | 改正法が公布済みで未施行ではないか。参照元が改正前の条文を引いていないか | 二次記事の引用が改正前の条文で、要件そのものが変わっていた |
| **義務の強さ** | 法律上の義務 / 努力義務 / ガイドライン上の推奨 / 単なる実務慣行。罰則の有無と重さ | 努力義務に過剰なコストをかけ、罰則付きの本当の義務を落とす |
| **規範の階層** | 法律 → 政令 → 省令 → 告示 → ガイドライン → Q&A。**どの階層に書いてあるか** | ガイドラインの記述を法律上の義務として説明し、相手に押し返されて主張が崩れる |
| **例外・適用除外** | ただし書き、除外規定、小規模事業者の特例 | 本文だけ読んで結論を出し、ただし書きで結論が逆になる |
| **実務上の運用** | 所管官庁の Q&A、パブリックコメントへの回答、事例集、通達 | 条文上あいまいな箇所を自己解釈で決め、公式 Q&A に真逆の回答が載っている |
| **判断の限界** | 個別事案の当てはめ・有効性判断は有資格者の領分。どこまでが調査で、どこからが相談か | 「たぶん大丈夫」で契約や運用を開始し、後から覆せない状態で問題が出る |

> 制度調査の成果物には**必ず「参照した条文の版と施行日」を書く**。日付のない法令調査は、半年後に再利用できない。契約条項の当てはめまで行くなら `dept-legal` に渡す。

## 4. 市場・競合の調査

| 軸 | 具体的に何を見るか | この軸を見落とすと起きること |
|---|---|---|
| **市場の定義** | その「市場規模」の分子と分母に何が含まれるか。調査主体ごとに定義が違う | 「市場規模 5 兆円」の 8 割が、自分が絶対に売れない領域だった |
| **数字の出所と推計方法** | 実測(統計・開示資料)か推計か。推計なら前提条件。**発表主体の利害** | ベンダーが自社レポートで出した市場規模を根拠に事業計画を立てる |
| **時点と単位** | 何年の数字か。暦年 / 年度、名目 / 実質、税込 / 税抜、為替レート、単位(千 / 百万) | 年度と暦年の数字を並べて成長率を計算し、存在しない伸びを報告する |
| **競合の粒度** | 直接競合 / 代替手段 / 内製 / 何もしない、の 4 段で並べる | 同種プロダクト同士で比較し、実際の最大の競合が表計算ソフトと手作業だったと後で知る |
| **価格の実態** | 公開価格と実勢価格の差。初期費用、最低契約、値引き慣行 | 公開価格だけで比較表を作り、実際の成約価格が半分だったと商談で知る |
| **参入障壁と、席が空いている理由** | なぜ今そこが空いているのか。過去に誰が試して何が起きたか | 空いているのではなく、複数社が試して撤退した跡地だった |
| **顧客の実在** | 「あったら使う」ではなく**金を払った実績**。要望と発注を分けて数える | 要望の数を需要と読み、作った後で誰も買わない |
| **情報の鮮度** | 撤退・買収・値上げ・新規受付停止。比較対象が今も売られているか | 比較表に載せた製品が、半年前に新規受付を停止していた |

> 市場調査の数字は**必ず出所と年を併記する**。出所のない数字は、report の中で最も速く陳腐化し、最も長く信じられてしまう。

# 文書テンプレート集

**テンプレートは埋める枠ではなく、削る出発点。** 該当しないセクションは消す。見出しだけ残して中身を薄める書き方が一番読まれない。

使う前に SKILL.md の「着手前に確定させる 4 点」を埋める。とくに**読後に何をしてほしいか**が決まっていないと、どのテンプレも選べない。

| 相手にしてほしいこと | 使うテンプレ |
|---|---|
| 発注・契約を判断してほしい | 提案書（社外向け） |
| 承認・決裁がほしい | 提案書（社内・決裁を取る） |
| 状況を把握してほしい | 進捗報告 |
| 事故の影響を把握し、再発防止を判断してほしい | 障害・インシデント報告 |
| 決定と宿題を確認してほしい | 議事録 |
| 動いてほしい | 依頼・相談のメール |
| 知っておいてほしい・従ってほしい | お知らせ・アナウンス |
| 断りを受け入れてほしい | 断りの連絡 |

## 共通ルール

- **冒頭 3 行が本体。** 決裁者はそこしか読まない前提で書く。入れるのは「何の件か」「相手に何をしてほしいか」「期限」
- **埋まらない箇所は `【要確認】` を残す。** 数字を推測で埋めない
- **セクションを削る。** Slack に流す報告に 6 セクションは要らない

---

## 提案書（社外向け）

最初の 3 行で受け取るもの: **何を提案しているか / いくらか / いつまでに返事が要るか。**

```markdown
# （提案の名前。「〜のご提案」ではなく、中身が分かる名前）

（3 行。何を・いくらで・いつから。ここだけで発注可否を検討できる粒度）

## ご提案の背景
（相手が言ったことを、相手の言葉で書く。こちらの憶測を混ぜない。
  ここがずれていると、以降は読まれない）

## ご提案内容
（何をするか。作業範囲を動詞で書く。「支援します」ではなく「〜を作ります」）

## 進め方とスケジュール
（フェーズ / 期間 / 各フェーズの成果物。表にすると速い）

## お見積り
（金額・内訳・前提条件。「別途お見積り」を残さない）

## 前提と、含まないもの
（範囲外を明記する）

## ご判断いただきたいこと / 次のステップ
（いつまでに何を返事してほしいか。次の打ち合わせ日程まで書く）
```

> 「含まないもの」を省かない。**提案書で揉めるのは、書いてある範囲ではなく書いていない範囲。**

## 提案書（社内・決裁を取る）

最初の 3 行で受け取るもの: **何を承認してほしいか / いくら・何人日か / 承認しないとどうなるか。**

```markdown
## 承認のお願い
（1〜3 行。「〜について、◯◯円 / ◯人日の実施を承認いただきたい」まで言い切る）

## 現状と課題
（事実と数字。「困っています」ではなく「月 20 時間かかっています」）

## やること
（実施内容・範囲・担当）

## 費用・工数・期間
（表。既存予算内か追加かを明記）

## リスクと対応
（都合の悪いことを先に書く。書かなければ決裁者は必ず聞いてくる）

## やらない場合どうなるか
（承認しない選択肢のコスト）

## 判断していただきたいこと
（承認 / 差し戻し / 条件付き承認。期限）
```

> 実質の説得材料は「やらない場合どうなるか」。**ここが書けないなら、その提案はまだ通らない。**

## 進捗報告

最初の 3 行で受け取るもの: **予定どおりか / 遅れているなら原因は何か / 自分に依頼が来ているか。**

```markdown
## サマリ
（3 行。順調 / 遅延 / 要判断 のどれかを最初に言う）

## 進んだこと
（完了したもの。「対応中」は進んだことではない）

## 遅れ・詰まっていること
（原因と挽回見込みをセットで。隠すと後で倍の説明が要る）

## 次の期間にやること
（担当と期限）

## 相談・依頼
（相手に動いてほしいこと。無ければ「なし」と書く）
```

> 「順調です」だけの報告は情報量ゼロ。**順調なら、何がどこまで終わったかを 1 行足す。**

## 障害・インシデント報告

最初の 3 行で受け取るもの: **今も起きているのか / 誰にどんな影響が出たか / 自分は何をすればいいか。**

一報と最終報告を分ける。**一報は原因が分からなくても出す。**

```markdown
## 状況（一報 / 続報 / 最終報告 のどれか）
（復旧済みか継続中か。最初に書く）

## 影響
（対象・件数・期間。「一部のユーザー」ではなく「◯◯機能を使う約 N 件」）

## 事象
（時系列。発生時刻・検知時刻・復旧時刻を明記）

## 原因
（判明していなければ「調査中」。推測を原因として書かない）

## 対応
（済んだこと / これからやること。担当と期限）

## 再発防止（最終報告のみ）
（仕組みで防ぐ策。「注意する」「気をつける」は再発防止ではない）
```

> 一報で求められるのは原因ではなく**影響範囲と現在の状態**。原因調査を待って報告を遅らせない。

## 議事録

最初の 3 行で受け取るもの: **何が決まったか / 自分に宿題があるか / 期限はいつか。**

```markdown
日時 / 場所 / 参加者（所属付き。欠席者も書く）

## 決まったこと
（1 行 1 決定。「〜で合意」まで言い切る。言い切れないものは下のセクションへ）

## 宿題
| 誰が | 何を | いつまでに |
|---|---|---|

## 決まらなかったこと / 持ち越し
（保留の理由と、判断に必要な材料）

## 議論の要点
（結論に至った理由。反対意見が出たなら残す。発言録ではない）
```

> **発言の時系列を上に置かない。** 読み返す人が探しているのは「決まったこと」と「自分の宿題」であって、誰が何を言ったかではない。
>
> 決定も宿題も 1 つも書けない会議は、議事録の前に会議の設計を疑う。

## 依頼・相談のメール

最初の 3 行で受け取るもの: **誰への依頼か / 何をしてほしいか / いつまでか。**

```markdown
件名: 【依頼】◯◯の確認（〜◯月◯日）
（件名に用件と期限を入れる。「ご相談」だけの件名は開かれない）

（宛名）

（1〜2 行。何の件で、何をしてほしいか。挨拶に 3 行使わない）

■ お願いしたいこと
（動詞で書く。「ご確認ください」ではなく「◯◯が正しいか見て、違えば指摘してください」）

■ 期限
（日付。「お手すきの際に」は期限ではない）

■ 背景
（なぜ必要か。短く。これを読まなくても動ける位置に置く）

■ 判断材料
（添付・リンク・前提。相手が探さずに済むように）
```

> **依頼と背景の順番を逆にしない。** 背景から書くと、最後まで読まないと何をすればいいか分からない。
>
> 相談は「A と B で迷っています。私は A を推します」まで書く。丸投げの相談は返事が遅れる。

## お知らせ・アナウンス

最初の 3 行で受け取るもの: **いつから何が変わるか / 自分に関係があるか / 何かする必要があるか。**

```markdown
## 件名（いつから何が変わるかを、件名で言い切る）

## 変更内容
（いつから / 何が / どう変わる。before → after の表が速い）

## 対象
（誰に関係するか。関係ない人が読まずに済むよう、前のほうに置く）

## お願いすること
（読み手の作業。無いなら「対応は不要です」と明記する）

## 理由
（納得が要る変更のときだけ。短く）

## 問い合わせ先
（人か窓口を名指しする。「担当まで」と書かない）
```

> 「対応は不要です」を省かない。**書かないと、全員が「自分は何かするのか」を考える時間を使う。**

## 断りの連絡

最初の 3 行で受け取るもの: **断りであること / 理由 / 代わりにできること。**

```markdown
（宛名）

（1〜2 行。結論。「今回は見送らせてください」を最初に書く）

（理由。1〜2 文。嘘をつかない。言えない事情なら「社内の事情で」と書き、詳細を作らない）

（代案。時期をずらす / 範囲を狭める / 別の担当を紹介する。無ければ書かない）

（今後の関係についての一文。社交辞令は 1 文まで）
```

> **断りを先延ばしにしない。** 曖昧な保留は相手の時間を奪う。断ると決めた日のうちに送る。
>
> 理由を盛らない。理由が多いほど言い訳に見える。

---

## テンプレを増やすとき

実際に書いた文書で、同じ構成を 2 回以上使ったらここに足す。1 回しか使っていない構成は足さない。足すときは「最初の 3 行で受け取るもの」と、各セクションに何を書くかの注記を必ず付ける。見出しの並びだけのテンプレは役に立たない。

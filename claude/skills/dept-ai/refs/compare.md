# 用途別の比較の型

**このファイルも値を持たない。** 持つのは「**何を軸に比べるか**」と「**その軸を公式ページのどこで読むか**」と「**その数値では分からないこと**」の 3 つだけ。数値は毎回 [sources.md](sources.md) の当て先から取る。

> **用途を確定させるまで比較を始めない。** 「どれが一番いい?」には答えがない。用途が決まって初めて軸が決まり、軸が決まって初めて表が書ける。用途が曖昧なまま全スペックを並べた表は、判断材料ではなくノイズ。

## 全用途に共通する前提

| 原則 | 中身 |
|---|---|
| **軸を先に、値を後に** | 見る軸を決めてから WebFetch する。開いてから「何を見るか」を考えると、目についた数字を全部並べてしまう |
| **同じ条件で並べる** | 単価は入力/出力で別、単位も提供元でズレる。**表に入れる前に単位を揃える。** 揃わないものは揃わないと書く |
| **今の不満から出発する** | 「速い/賢い」ではなく「**今どこで詰まっているか**」。詰まっていないなら乗り換えの理由がない |
| **覆る条件を書く** | 推奨には必ず「この前提が崩れたら別の答えになる」を添える。前提を書かない推奨は再利用できない |

## コードを書かせる

**エージェント用途と単発生成は別物。** 同じ「コード」でも見る軸が違う。混ぜて比べない。

### エージェント用途（CLI に何十ターンも走らせる）

| 軸 | どこで読むか | この数値だけでは分からないこと |
|---|---|---|
| ツール呼び出しの精度・安定性 | 公式ページには載らない | **ここが本丸。** 実測でしか分からない。長い作業で「途中で指示を見失う」「同じ失敗を繰り返す」が起きるか |
| コンテキスト長 | モデル一覧ページのスペック欄 | 長い作業ほど累積で効く。ただし**長い＝使い切れる**ではない（後述「長文を読ませる」） |
| 出力上限 | モデル一覧ページのスペック欄 | 大きな差分を一度に吐けるか。上限に当たると分割の手間が乗る |
| 実効コスト | 料金ページ（入力/出力 + キャッシュ） | **1 回の単価ではなく 1 タスク完遂までの総額で比べる。** 安いモデルが往復数を増やして高くつくことがある |
| 推論の強さを調整する仕組み | モデル一覧・機能ドキュメント | 段階が用意されている場合、**モデルを変えるより先にこれを上げ下げする方が効くことがある** |
| CLI 側の対応 | Claude Code / Codex CLI / Gemini CLI の各ドキュメント | **モデルが出ても手元の CLI が指定できるとは限らない。** モデル指定の方法とサポート状況を CLI 側で確認する |

### 単発の生成（1 回のやり取りで完結）

| 軸 | どこで読むか | この数値だけでは分からないこと |
|---|---|---|
| 一発の正確さ | 公式ベンチマーク（下の注意を必ず読む） | 自分の言語・フレームワーク・社内規約での正確さ |
| レイテンシ | モデル一覧ページの速度欄（相対表現のことが多い） | 相対表現は同一提供元内でしか比較できない。**他社と横並びにしない** |
| 単価 | 料金ページ | 単発なら総額が小さく、価格差はたいてい判断を左右しない。**速さと正確さで決める** |

> **単発なら安いモデルで足りることが多い。** 高いモデルが要るのは、失敗のやり直しコストが単価差を上回るとき。

## 長文を読ませる

| 軸 | どこで読むか | この数値だけでは分からないこと |
|---|---|---|
| コンテキスト長 | モデル一覧ページ | **入る ≠ 使える。** 上限近くで指示追従や中盤の情報の拾い漏れが悪化するかは書いていない |
| 長文時の課金の効き方 | 料金ページ | 長い入力に別単価・割増が設定されている場合がある。**「入力単価 × 文字数」で暗算しない**。料金ページに長文専用の記述がないか探す |
| キャッシュ | 料金ページのキャッシュ節 | **同じ長文を繰り返し読ませるならここが総額を決める。** 書き込みと読み出しで単価が別、有効期間もある |
| トークン化の効率 | モデル一覧・料金ページの注記 | **同じ文章でもモデルによってトークン数が変わる。** 世代更新でトークナイザが変わった旨の注記があれば、単価が同じでも実質の値段が変わる。日本語は特に効く |
| 出力上限 | モデル一覧ページ | 長文を読ませた結果を長文で返させるなら、入力より出力上限が先に効く |

> **長文用途の比較は「単価表」では終わらない。** ①長文専用の課金 ②キャッシュ ③トークン化の効率 の 3 つを踏まないと、実際の請求と 2〜3 倍ずれる。
>
> **公式が長文性能を保証しているわけではない。** 上限まで入ることと、上限まで入れて品質が保たれることは別。**判断が重要なら実測する**（後述）。

## 大量処理・コスト重視

| 軸 | どこで読むか | この数値だけでは分からないこと |
|---|---|---|
| 入力/出力の単価差 | 料金ページ | **出力は入力より高いのが通例。** 入出力比が読めていないと見積もりが外れる。**先に自分のワークロードの入出力比を出す** |
| バッチ | 料金ページのバッチ節 | 割引率と引き換えに遅延がある。**締め切りのある処理には使えない** |
| キャッシュ | 料金ページのキャッシュ節 | 何回読み出せば元が取れるかは、書き込み単価と読み出し単価の比から自分で計算する |
| 割引の重ねがけ | 料金ページ | バッチとキャッシュを併用できるか、地域指定などの割増が上に乗るかは提供元ごとに違う |
| レート制限 | レート制限ページ | **「安いが流量が出ない」で詰まる。** 単価だけ見て量が捌けるかを見ないのが典型的な失敗 |
| 処理方式の選択肢 | 料金ページ | 同じモデルに複数の単価行が並ぶことがある。**どの行で見積もったかを明記する** |

> **大量処理は「単価 × 件数」では終わらない。** 実効コストは `(入力単価 × 入力量 + 出力単価 × 出力量) × 割引の掛け合わせ` であり、そこにレート制限という上限が別途かかる。
>
> **無料枠は見積もりの根拠にしない。** 提供元によっては無料枠と有料枠で制限も条件も別建て。**本番前提なら有料枠の行を読む。**

## 対話・壁打ち

**公式ページで比べられることが一番少ない用途。** スペックで決まらないので、ここは実測の比重を上げる。

| 軸 | どこで読むか | この数値だけでは分からないこと |
|---|---|---|
| レイテンシ | モデル一覧ページの速度欄 | 対話では体感がほぼ全て。**相対表現は他社と比較できない**ので、実測で並べる |
| コンテキスト長 | モデル一覧ページ | 会話が伸びたときにどこで破綻するか |
| 応答の粒度・言い回し | **どこにも書いていない** | 冗長さ、断定の強さ、反論してくるか追従するか。**好みの問題で、他人の評価が当てにならない領域** |
| 日本語の質 | **どこにも書いていない** | 多言語対応と日本語が自然かは別。実測必須 |

> **この用途は「安い方で試して不満が出たら上げる」でよい。** 事前比較に時間をかけても、実際に数日使うまで分からない。

## 画像・音声

| 軸 | どこで読むか | この数値だけでは分からないこと |
|---|---|---|
| そもそも対応しているか | モデル一覧ページの入出力欄 | **入力対応と出力対応は別。** 「画像を読める」と「画像を作れる」を混同しない |
| 課金単位 | 料金ページ | **テキストと課金単位が違う**ことがある（枚数・秒数・解像度など）。トークン単価の感覚で見積もらない |
| 専用モデルの有無 | モデル一覧ページ | 一覧に汎用モデルと専用モデルが同居している。**用途に専用モデルがあるならそちらが基準** |
| 対応形式・上限 | モデルごとの機能ドキュメント | 扱えるファイル形式・サイズ上限・言語。**一覧ページには載らないので個別ページまで降りる** |

> **画像・音声はモデル一覧ページの粒度では判断できない。** 一覧で候補を絞り、**必ず個別の機能ドキュメントまで降りてから**答える。

## 手元で実測して比べる

**この部署が持てる唯一の固有情報がここ。** 公式サイトにもベンチマークにも「自分の用途での得手不得手」は載っていない。

### 手順

1. **お題を 1 つに決める。** 自分が実際に困った具体的なタスク（このリポジトリの実ファイル、実際に書いた仕様）。抽象的なお題は差が出ない
2. **評価軸を先に書き出す。** 出力を見てから基準を決めると、好みの出力を後付けで正当化してしまう。例: 正しく動くか / 指示した制約を守ったか / 余計なことをしていないか / 何往復かかったか
3. **同じ入力を両方に投げる** — `/codex` と `/gemini` を使う。**同一セッション内で並列に投げる**（時間を空けると、その間にモデル側が変わる）
4. **出力を保存する。** 記憶で比べない。ファイルに落として並べる
5. **軸ごとに評価して、結論と一緒に「いつ・どのモデルで測ったか」を書く**

### 公平に比べるための注意

| やること | なぜ |
|---|---|
| **プロンプトを完全に同一にする** | 片方だけ言い回しを足すと、モデル差ではなくプロンプト差を測ることになる |
| **モデルを明示的に固定する** | 既定モデルは黙って変わる。**どのモデルで測ったか分からない結果は再現できない** |
| **同じファイル・同じ量のコンテキストを渡す** | 片方だけリポジトリを読めている状態で比べない |
| **リトライを禁じる** | 気に入らない出力を引き直したら、それは「良い出力が出る確率」を測っていない |
| **順番の影響を疑う** | 自分の評価は先に見た方に引きずられる。判断が割れたら、順番を入れ替えてもう一度 |
| **1 回で決めない** | 出力はブレる。1 回の勝敗は運。**差が小さいなら「差が出なかった」と書く** |
| **CLI の差とモデルの差を分ける** | ツール実行の作法・サンドボックス・既定の饒舌さは CLI 側の性質。**モデルの優劣として報告しない** |

> **実測は「勝者を決める」ためではなく「自分の用途で差が出るか」を見るためにやる。** 差が出ないなら、安い方・手に馴染んだ方でよい。それも立派な結論。
>
> **測った結果は SKILL.md の「育て方」に従って追記する。** 残さない実測は、次回また同じ時間を払うだけ。

## ベンチマークの読み方

**各社は自社に有利な条件を選んで出す。** 嘘ではないが、公平でもない。以下を確認してから引用する。

| 確認すること | 見落とすとどうなるか |
|---|---|
| **比較相手が現行か** | 他社の 1 世代前と比べていることがある。「勝っている」の相手を必ず見る |
| **自社と他社で条件が揃っているか** | 自社だけ推論を強めた設定・自社だけ特定の足回り付き、といった非対称がある。脚注に書いてある |
| **評価対象のバージョン** | 「同名だが別スナップショット」で数字が変わる。**モデル ID まで確認する** |
| **コンテキスト条件** | 短い入力での成績は、長文を流し込んだときの成績を保証しない |
| **試行回数と集計方法** | 複数回試して最良を採る集計は、1 回の実用と数字が一致しない |
| **測定日** | ベンチマーク公表後にモデル側が更新されていれば、その数字はもう対象を指していない |
| **自分の用途との距離** | 一般的なコーディング指標が高いことと、**自分のフレームワーク・自分の日本語仕様で強い**ことは別 |

> **ベンチマークは候補を絞るまで。** 最終判断は自分の用途での実測に置く。**ベンチマークの数字を根拠に乗り換えを勧めない。**
>
> **第三者ランキングも一次情報ではない。** 集計条件と更新日が分からないものは引用しない。引用するなら、その条件と日付ごと書く。
